# 分心/疲劳驾驶实时检测系统 —— 技术方案

## 1. 问题定义

驾驶员监控系统（DMS）要在**不接触驾驶员**的前提下，从普通单目摄像头的画面里
判断其当前状态。本系统识别四类状态，并按风险分级预警：

| 类别 | 含义 | 风险 |
|---|---|---|
| `normal` | 正常驾驶 | — |
| `glance` | 短暂扭头（看窗外 / 看中控） | 视线离路，短时风险 |
| `phone` | 持续低头看手机 | 视线 + 单手离开方向盘 |
| `fatigue` | 疲劳点头 | 微睡眠，最高风险 |

### 1.1 两个核心难点

**难点一：`phone` 与 `fatigue` 在单帧上无法区分。**

两者都是"低头"，头部俯仰角完全一致。区别只在**时间维度**——疲劳点头是
**周期性前倾-回弹**，看手机是**静态保持**。

这一条决定了整个方案的技术选型：模型**必须是时序模型**，输入**必须是一段序列**，
不能是单帧姿态分类器。后文第 5 节关于窗口长度的讨论，本质上是在为这个区分服务。

**难点二：预警必须快，但时序模型天然带延迟。**

"动作变了之后灯多久才亮"是这类系统的核心体验指标，慢了就是产品缺陷。
本方案把延迟当成一等指标逐段测量并优化，而不是拍一个"约几秒"（第 5、7 节）。

### 1.2 系统链路

```
摄像头 15 fps
   │
   ├─ 支路一（骨骼路）
   │    MediaPipe Pose（33 关键点）
   │      ↓ 归一化（肩中点 + 3D 肩宽）
   │      ↓ 滑窗 45 帧 @ 15 fps = 3.0 s
   │    PoseTransformer（16.2 万参数，CPU 前向 < 5 ms）
   │      ↓ 4 类概率 → EMA
   │
   └─ 支路二（面部路）
        MediaPipe FaceMesh（478 点）→ EAR / MAR / 头部欧拉角
          ↓ 17 s 滑窗统计：PERCLOS / 眨眼率 / 点头次数 / 哈欠秒数
        前 3 个进逻辑回归 → P(fatigue)（哈欠走规则，不进回归）
   │
   ├─ 融合闸门：支路一判"正视前方"时，支路二才允许投票（权限封顶 L2）
   ↓
分级预警状态机（阈值迟滞 + 时间迟滞 + EMA）
   ↓
灯光（绿/黄/橙/红） + 语音提示
```

全链路在 CPU 上实时运行，**不需要 GPU**。

两条支路**互补而不是冗余**：支路一判的是"头下垂的运动模式"，对"闭着眼睛但头
稳稳不动"这一类几乎没有响应（骨骼序列里它和"正常坐着"长得一样）；支路二直接
读脸，补的正是这一类。代价是支路二需要 27 秒连续可用的输入才能出第一个数，
细节与实测见第 8 节。

## 2. 数据采集与划分

### 2.1 采集协议

- 4 类 × 每类 ≥ 6 段，每段 ≥ 10 秒，**每段只做一个动作**，段间留 2~3 秒空白。
- 采集程序 `tools/record.py` 按类别分目录、自动编号，录完当场给出"合格 / 建议重录"判定。
- 动作执行判据（录制时须照此执行，否则类别定义会漂移）：

| 类别 | 判据 |
|---|---|
| `normal` | 头部 yaw / pitch 在 ±15° 内；允许自然看一眼后视镜，但 < 0.5 s 且回到正视 |
| `glance` | 单次侧向偏转**持续 > 1 s** |
| `phone` | pitch 前倾 **> 25° 且持续 > 2 s**，静态保持 |
| `fatigue` | pitch **周期性**前倾-回弹，周期 1~4 s |

### 2.2 数据集划分：按片段整体划分（关键实验设计）

**这是本项目最重要的实验设计决策。**

滑窗步长 15 帧、窗口长 45 帧，相邻窗口**重叠 30 帧（67%）**——它们几乎是同一条数据。
如果按**窗口**随机划分训练/测试集，同一段视频里近乎重复的窗口会同时落进两侧，
测试准确率会虚高，而现场一坐上去就崩。

因此 `tools/build_dataset.py` **按录制片段整体划分**：比例 0.75 / 0.125 / 0.125，
随机种子固定为 42。当前 106 段素材实际切出 **82 / 12 / 12 段**
（每类 26~27 段 → 20~21 训练 / 3 验证 / 3 测试；24 段时代是每类 6 段 → 4 / 1 / 1）。

**这样得到的测试集是模型完全没见过的坐姿与光照**，才是有意义的泛化度量。

### 2.3 时间轴对齐

UVC 摄像头的帧率**会被自动曝光拖低**（实测同一摄像头：光线正常 30 fps、
偏暗 10 fps、镜头全遮 1 fps），而驱动报告的帧率是恒定的。若按名义帧率写盘，
视频时间轴会整体压缩——实测真实 25.2 秒只存成 8.4 秒（3 倍速）。

本方案在**两端用同一套规则消除这个不确定性**：

- **采集端**：不信任名义帧率，按**墙上时钟**把画面重采样到 `TARGET_FPS`（15 fps），
  不够就重复上一帧、多了就丢；帧先编码成 JPEG 攒在内存，停止时一次性写盘
  （mp4 帧率必须提前定，而真实时长只有录完才知道）。
- **推理端**：同样按 15 Hz 的墙上时钟节拍取"当前最新的一帧"塞进滑窗，
  **不是"来一帧塞一帧"**；摄像头慢就自然重复帧。

这样保证"45 帧 = 3.0 秒"这个物理时长在训练数据和现场推流中是**同一个值**，
而不是靠"摄像头恰好跑在某个帧率"来保证一致。本机摄像头实测只有 10~11 fps，
这一条尤其要紧。

### 2.4 已知局限

当前 **106 段**素材（`normal` / `glance` / `phone` / `fatigue` 各 26~27 段）
全部采集自**同一场次、同一房间、同一光照**，测试集按**片段**整体留出
（同一段录像不会同时出现在训练和测试里，这一点是做到了），
但**不是跨域留出**。因此第 7 节的数字**不能作为现场性能指标**，
必须补采多环境数据后重测。详见 7.4 节。

⚠️ 素材规模变过（24 段 → 106 段），**文档里两组数字并存的地方都标了口径**；
引用时注意分母，两者不可比。

## 3. 特征提取与归一化

### 3.1 特征

每帧提取 MediaPipe Pose 的 33 个关键点，每点 `(x, y, z, visibility)` 共 4 维：
单帧特征维数 `33 × 4 = 132`。

### 3.2 归一化

- **原点**：左右肩（关键点 11、12）中点。
- **尺度**：3D 肩宽。

这样做使特征对**拍摄距离、身高、画面中位置**都不敏感，只保留姿态本身的信息。
肩宽序列再做滑动中位数平滑（窗长 15 帧），压掉单帧肩宽抖动的污染。

### 3.3 低置信点的处理

`visibility` 低于 0.5 的关键点，**坐标沿用该点上一帧的有效值**，不置零。
置零会让所有不可信点挤在原点，凭空造出并不存在的几何结构。

### 3.4 离线与在线的一致性

离线提取与实时推理**共用同一份 `src/pose.py`**（同一个模型文件、同一套置信度阈值、
同一套低置信处理）。各写一套会导致训练与推理的输入分布不一致，
现象是"离线测着很好、现场一坐就错"。

**唯一的、有意为之的差异**：肩宽平滑在离线用 `center=True`（能看到未来 7 帧），
实时只能用因果版本（`OnlineNormalizer`）。理由：肩宽是慢变量，15 帧窗口里
挪动 7 帧的影响远小于肩宽检测本身的抖动，且两侧都用中位数、对毛刺的鲁棒性一致。

这一处差异已记录在案，是**现场表现异常时的第一排查点**。修法是把离线也改成因果的
（`center=False`）重训一遍——趁数据量还小，越早改越便宜。

## 4. 模型

### 4.1 结构

`PoseTransformer`：

```
线性投影 (132 → 64)
  → 拼接 CLS token
  → 加可学习位置编码
  → 3 层 pre-LN TransformerEncoder（4 头，FFN 256，dropout 0.1）
  → LayerNorm + Linear → 4 类
```

| 项 | 值 |
|---|---|
| 参数量 | **161,988** |
| d_model / n_head / n_layer | 64 / 4 / 3 |
| 输入 | 45 × 132 |
| 输出 | 4 类 |
| CPU 单次前向 | **< 5 ms** |

### 4.2 设计选择及其理由

**CLS token 而非平均池化。** 平均池化把窗口内所有帧等同看待，而疲劳点头的关键信息
是**局部**的（某几次点头的波峰形态）。CLS token 让模型自己学会该关注哪几帧。

**pre-LN 而非 post-LN。** 小模型 + 小数据集上，pre-LN 的训练稳定得多。

**规模刻意做小。** 设计时数据量只有 24 段，更大的模型必然过拟合。
16 万参数在 CPU 上单次前向 < 5 ms，现场实时绰绰有余。
⚠️ 素材后来涨到 106 段，**这个规模没有再动**——但重训日志显示训练准确率第 6 轮就
到 100%、测试停在 80.1%，**过拟合依然存在**。下一步是补采数据，不是加大模型。

### 4.3 训练配置

AdamW，学习率 3e-4，weight decay 1e-4，batch size 64，label smoothing 0.05，
最多 60 轮，按验证损失早停（patience 15）。

### 4.4 ⚠️ 用验证损失选模型，不要用验证准确率

**这是一个真实踩过的坑，也是最能说明"汇总指标会骗人"的例子。**

初版 `train.py` 按**验证准确率**选最优权重并早停。但验证集只有 4 段、任务又简单，
**第 3 轮验证准确率就顶到 1.0000**，之后再也不可能"提升"——于是早停机制
白等了 15 轮、并保存了**第 3 轮的权重**。

后果极其隐蔽：**汇总准确率照样报 100%**，但模型的实际置信度只有 **0.52~0.62**
（4 类瞎猜线是 0.25）——只比瞎猜好一点点。现场换个坐姿，概率就会在阈值附近抖动，
灯光跟着乱闪。

改成按**验证损失**选最优 + 早停（带 `min_delta=1e-4` 防抖动）后：

| | 改前 | 改后 |
|---|---|---|
| 最优 epoch | 3 | 59 |
| 验证损失 | 0.6443 | **0.2212** |
| 验证准确率 | 1.0000 | 1.0000（饱和，无分辨力） |
| **P(真值)** | **0.52 ~ 0.62** | **0.90 ~ 0.93** |
| `fatigue` 段的 P(phone) | 0.153 | **0.028** |
| `phone` 段的 P(fatigue) | 0.179 | **0.021** |

**结论：已经饱和的指标没有分辨力，不能用来选模型。** 本项目所有模型选择
一律以验证损失为准。

## 5. 窗口长度：由实验确定，而非推理确定

### 5.1 最初的假设是错的

最初取 **60 帧（4.0 秒）**，理由是"窗口必须容纳一个完整的疲劳点头周期（1~4 秒），
否则 `fatigue` 和 `phone` 分不开"。

**这个说法从未被验证过。** 实测推翻了它。

### 5.2 实测：窗口长度对类别可分性的影响

`tools/sweep_window.py` 按不同窗口长度各重切数据集、各训一个模型：

⚠️ **口径**：下表是 **24 段时代**扫的（当时每类 6 段，测试集每类只留 1 段），
**数据集涨到 106 段后没有重扫**。所以表里的**百分比不能当性能指标看**
（`normal` 那一列尤其，分母只有 11 个窗口）；它要说明的是**趋势**——
窗口从 15 帧拉到 45 帧，丢的分全在 `normal` 上。
45 帧这个**结论**已被 106 段重训继承（重训数字见 4.4 与 7.3）。

| 窗口（帧） | 秒 | `normal` | `glance` | `phone` | `fatigue` | P(phone\|fatigue) | P(fatigue\|phone) |
|---|---|---|---|---|---|---|---|
| 15 | 1.0 | 23.1% | 100% | 100% | 100% | 0.026 | 0.019 |
| 20 | 1.3 | 7.7% | 100% | 100% | 100% | 0.023 | 0.069 |
| 30 | 2.0 | 0.0% | 100% | 100% | 100% | 0.019 | 0.019 |
| **45** | **3.0** | **81.8%** | **100%** | **100%** | **100%** | **0.023** | **0.015** |
| 60 | 4.0 | 100% | 100% | 100% | 100% | 0.019 | 0.017 |

**`fatigue` / `phone` / `glance` 在 15 帧（1.0 秒）下就已经全部 100%**，
混淆对概率 0.019~0.069。**1 秒的窗口照样能分开疲劳和看手机**——
"必须装下一个完整点头周期"的假设是错的。

丢掉的准确率**全部集中在 `normal` 一类**，且只集中在 `normal_03` 一个片段上
（标定显示其平均概率为 `nor=0.717 / fat=0.222`，非真值峰值 0.389，
是全场唯一一个"像疲劳"的正常片段）。

### 5.3 窗口长度直接决定响应延迟

窗口越长，模型看到的"新动作"占比越低，概率爬升越慢。`tools/sweep_step.py` 实测
阶跃响应延迟：

| 窗口（帧） | 秒 | 平均响应延迟 |
|---|---|---|
| 60 | 4.0 | 3.8 s |
| **45** | **3.0** | **1.0 s** |
| 30 | 2.0 | 1.6 s |

### 5.4 最终选择：45 帧（3.0 秒）

当时（**24 段时代**）在该配置下：留出片段的级别轨迹全部正确、零误报，
窗口级测试准确率 98.04%，混淆对概率 0.023 / 0.015。

⚠️ **98.04% 是 24 段的分母，不要再用。** 素材涨到 106 段后重新训练
（`runs/20260922_200934`，176 个测试窗），窗口级准确率是 **80.11%**、
宏平均 F1 0.800：`normal` 0.925 / `glance` 0.651 / `phone` 0.760 / `fatigue` 0.884
（召回）。**下降是正常的**——原来 24 段的测试集又小又同源。当前口径见 7.3 与 7.4。
窗口长度 45 帧这个**结论**没有变（重训仍用它），变的是性能数字。

**为什么不再往下压到 30 帧**：30 帧时 `normal_03` 的窗口 100% 被判成非 `normal`，
现场坐着不动灯就会亮。这是**数据问题**（24 段时代正常样本只有 6 段，其中一段本身偏），
不是窗口本身的问题——补采 `normal` 类数据后再压。

**判据是"在零误报的前提下哪个最快"，不是"哪个最快"。** 误报比慢难看得多。

## 6. 分级预警状态机

### 6.1 为什么必须做迟滞

模型输出的是逐次决策的概率。若直接用 `argmax` 驱动灯光，概率在 0.5 附近抖动一下
就会切换级别，现场看起来像设备坏了。本方案用三层滤波：

1. **阈值迟滞**：进入阈值 0.60 / 退出阈值 0.40
2. **时间迟滞**：升级需稳定 0.25 s，降级需稳定 1.0 s
3. **概率指数平滑（EMA）**：α = 0.55，决策频率 10 Hz

**降级刻意比升级慢——漏报比误报危险。**

这六个参数全部做成**命令行参数**，因为"反应快不快"必须在现场对着真人调：
同一组阈值在不同光照、不同人身上的表现差别很大，现场没有改代码重跑一轮的时间。

### 6.2 分级映射

| 级别 | 触发类 | 灯光 | 语音 |
|---|---|---|---|
| **L0** 正常 | `normal` | 绿，常亮 | — |
| **L1** 注意 | `glance` | 黄，1.2 Hz 闪烁 | — |
| **L2** 警告 | `phone` | 橙，3 Hz 闪烁 | "检测到持续低头看手机" |
| **L3** 紧急 | `fatigue` | 红，6 Hz 闪烁 | "检测到疲劳驾驶" |

L1 不发声是刻意的：瞟一眼后视镜也出声会把人烦死。同一级别最快 6 秒重念一次。

### 6.3 状态机参数的取值依据

默认值 `0.6 s / 2.0 s / α=0.30 / 5 Hz` 在实测中表现为"延迟太长"。用
`tools/lag_breakdown.py` 量出这四项的**全部改动加起来只值 0.8 秒**
（升级 3.7 s → 2.9 s，降级 6.5 s → 5.0 s），提速后 24 段的级别仍然全对、零误报，
因此放心调快。

## 7. 实测结果

### 7.1 响应延迟的拆解与优化

**测量方法。** 拿"`normal` 段 + 目标动作段"拼接，人为造出一个**阶跃**，
测"动作改变之后多久亮灯"。单个录制片段量不出这个数——它从头到尾只有一个动作，
第一帧输出时概率已经在顶上了。

**测量结果与优化：**

| 目标动作 | 优化前<br>（60 帧 / α0.30 / 5 Hz / 升 0.6 s） | 优化后<br>（45 帧 / α0.55 / 10 Hz / 升 0.25 s） |
|---|---|---|
| `glance` | 3.9 s | **1.6 s** |
| `phone` | 4.9 s | **0.4 s** |
| `fatigue` | 2.3 s | **0.9 s** |
| **平均** | **3.7 s** | **1.0 s** |
| 回到 L0 | 6.5 s | 5.3 s |

**两轮改动各值多少，是分开量出来的：**

- **状态机六个参数的全部改动只值 0.8 秒**（其中 EMA 占 0.2 s、时间驻留占 0.25 s）。
- **降低阈值几乎没用**：阈值从 0.60 降到 0.50 只快 0.1 s。**瓶颈不是阈值。**
- **真正的大头是"模型概率爬升"（0.9~3.7 s），而它由窗口长度决定。**
  窗口从 60 帧降到 45 帧又砍掉 1.9 秒。

冷启动时滑窗需要填满才有第一次输出，45 帧即额外 3.0 秒——持续运行时不计这笔。

（降级回到 L0 仍需 5.3 s：`EXIT_TH=0.40` 比 `ENTER_TH=0.60` 低得多，
且概率本身要随窗口内容退出去。这是刻意设计的——灯光频繁闪烁比慢更难看。）

### 7.2 类别可分性：模型学到的是时间结构

`tools/replay_clip.py` 把单个片段逐帧过模型，重点看**类间**的分离：

| 片段类型 | P(fatigue) | P(phone) |
|---|---|---|
| `fatigue` 片段 | **0.92** | 0.028 |
| `phone` 片段 | 0.021 | **0.93** |

两类**低头幅度完全相同**，模型靠的是周期性把它们分开。
**这张表证明模型学到的是时间结构，而不是"低头幅度"这个捷径。**

> 补充说明：片段内部 P(fatigue) 几乎是平的（标准差 0.0007~0.0075），
> 因为 3 秒窗口必然包含至少一个完整点头周期，所以每个窗口都"像疲劳"。
> 模型是**窗口分类器**而不是逐帧分类器，输出与点头相位无关。
> 这是好性质：**实时灯光不会随点头上下抖动。**

### 7.3 现场实测：摄像头 + 真人

用 `src/live.py --log-probs` 记录每次决策的概率，实拍一次连续疲劳动作：

| 时间段 | 观察 |
|---|---|
| 3.6 ~ 9.0 s | `nor` 0.75~0.81，`fat` ≤ 0.20 —— 正常坐姿 |
| 9.0 ~ 10.7 s | `fat` 0.44 → 0.71 —— 开始点头 |
| **10.7 s** | **进入 L3（紧急），语音播报**，响应延迟约 1.7 s |
| **10.7 ~ 31.5 s** | **`fat` 稳定在 0.70~0.89，级别连续保持 L3，一次未掉** |
| 31.5 ~ 40.6 s | `fat` 0.77 → 0.30，迟滞使级别维持到 |
| **41.9 s** | 回到 L0 |
| 41.9 ~ 59.8 s | `nor` 0.66 → 0.89 —— 干净恢复 |

**`fat` 峰值 0.89**，与录制片段上的 0.92 属同一水平。

**结论：模型在活人身上并不"没把握"，其置信度与训练数据一致。**
（此前曾观察到"现场峰值只有 0.64"，后经复测确认是测量时头部偏转造成的，
不是模型问题。）

### 7.4 ⚠️ 局限（必须在报告中如实说明）

1. **数据全部来自同一场次、同一房间、同一光照。** 测试集按**片段**整体留出
   （无同段泄漏），但不是**跨域**留出。**0.8011 不能作为现场性能指标**，
   补采多环境数据后需重测。
2. 每类 26~27 段，已达成"每类 20~30 段"的目标，**数据量不再是最大瓶颈，
   环境与参与者的多样性才是**。
3. 参与者只有 1 人，未验证跨人泛化（支路二的真人验证同样是单人，见第 8 节）。
4. 离线与在线存在一处已知的归一化差异（见 3.4 节）。
5. **最薄弱的一类是"轻微分心"**：`glance` 召回只有 0.651（15/43 被判成
   `normal`），`phone` 有 12/50 被判成 `glance`。反过来 `fatigue` 是最稳的
   （精确率 0.927 / 召回 0.884 / F1 0.905）。**报性能时要报这张分栏表，
   不要只报一个汇总准确率**——汇总数会把"漏报集中在哪"这个关键信息抹掉。
6. **支路二有它自己的局限**（27 秒冷启动；真实驾驶场景下闸门会频繁关闭），
   单独列在第 8 节末尾，写材料时不能省。

## 8. 第二条支路：面部路与融合闸门

### 8.1 为什么不把它并进支路一

支路一判疲劳靠的是**头下垂的运动模式**。而"闭着眼、头稳稳不动"这一类，
在骨骼序列里和"正常坐着"几乎没有差别——不是模型不够强，是**输入里没有那个信息**。
面部路（EAR/MAR/头姿）才有。两条支路是**互补**关系，不是冗余。

### 8.2 特征与归一化

每帧从 FaceMesh（478 点）算三个量：**EAR**（眼睛纵横比）、**MAR**（嘴）、
**头部欧拉角**（pitch 为主）。再在 17 秒滑窗上统计出：

| 统计量 | 含义 | 是否进模型 |
|---|---|---|
| `perclos` | 窗内 EAR_norm 低于阈值的比例 | ✅ |
| `brate` | 眨眼率（次/分） | ✅ |
| `nod` | 点头次数 | ✅ |
| `yawn_sec` | 连续张嘴超过 `YAWN_THR` 的秒数 | ❌ 走规则 |

**归一化是这一路的核心难点**：EAR 的绝对值因人、因镜头距离而变，所以每个点
要除以"自己的基线"——**取该点之前 10 秒窗内 EAR 的 75 分位**（按时间戳选窗，
不按帧数，因为摄像头帧率会漂）。

**为什么必须是 p75 而不是中位数**：中位数在闭眼占比超过 50% 时会被闭眼自己
拽塌，`EAR/基线` 恒等于 1——**越疲劳越读不出来**（自我抑制）。实测标了 11 次
主动闭眼：中位法只检出 4 次，p75 检出 10 次；离线 `fatigue` 分离度 3.3× → 5.4×。
阈值随之重标定为 **0.80**。

`r(EAR, eyeBlink) = −0.96`（眼镜反光没有毁掉这个量）。

⚠️ **p75 自己有个硬上限**：它只在"窗内闭眼占比 c < 约 0.75"时才落得回睁眼区间。
闭眼 12 秒就把 10 秒窗填满，基线塌到闭眼值上，后果是**闭着的眼睛读成"睁着"**
（`EAR_norm ≈ 0.93`），**睁开之后**更荒唐（`EAR_norm ≈ 2.0`）。这条是实测出来的，
它直接决定了 8.6 的录制 protocol。

### 8.3 逻辑回归，以及一个必须说清的循环论证

3 个特征标准化后进逻辑回归（平衡准确率 71.4%，置换检验 p = 0.000）。

**`perclos` 的标准化系数是 +0.859**——它是模型自己的输入特征。所以
"`P(fatigue)` 和 PERCLOS 高度相关"这件事是**机械的**，不是证据。
真正要问的是"PERCLOS 本身可不可信"，而 PERCLOS 由 EAR_norm 定义，
EAR_norm 由 8.2 的基线定义。**证据链要一路退到原始 EAR 才算数。**

⚠️ **离线数据做不到这个归因**：26 段 `fatigue` 里有 **25 段头动 > 10°**，
也就是说"它到底是靠眼睛还是靠头动"在离线片段上**证不出来**——
这也是必须做真人会话验证的原因。

### 8.4 融合闸门：它不是"融合"，是**否决权**

```python
gate = (argmax(branch1.ema) == "normal") and (branch1.ema["normal"] >= GATE_MIN)
```

**`GATE_MIN = 0.60` 是推导出来的，不是调出来的**：四类 EMA 非负且和为 1，
所以 `ema[normal] >= 0.60` ⟺ 三个非 normal 类之和 ≤ 0.40 ⟺ **每一个**非 normal
类都 ≤ `EXIT_TH = 0.40`。改这个数就是改"闸门比降级判据严多少"。

三条配套决策：
1. **权限封顶 L2**：`L_fused = max(L1, min(L2, 2))`。看到 L3 就一定来自支路一。
   理由：支路二的标定集太小，撑不起"紧急"这一级。
2. **闸门关闭时不往缓冲写帧**。扭头期间 EAR 被头姿污染，照写的话闸门一重开就误报。
3. **哈欠走规则不进回归**。训练集 96 段里 0 段有哈欠，`yawn` 列恒等于 0，
   系数必然是 0.000——那是**常数**，不是"这个特征没用"。

### 8.5 `HIST_SEC = 27 s` 是**充要条件**，所以离线验不了支路二

统计窗里每个样本都要有自己的完整 10 秒基线史，因此缓冲必须留
`HIST_SEC = WIN_SEC(17) + ROLL_WIN(10) = 27` 秒，少一秒都不够。

**后果很硬**：训练片段的中位长度是 17.1 秒，**没有一个片段能让支路二出数**。
所以离线回放里"支路二没有误报"其实是"**它没跑**"，不是"它跑对了"。
`tools/replay_fuse.py` 里有专门的检查（check 0.5）把这两件事分开。
**支路二只能靠真人不间断 27 秒以上来验证。**

### 8.6 真人会话验证：方法与 protocol

工具：双击 `live_fuse.bat`（日志自动存 `runs\sessionN.csv`，不覆盖）。
闭眼时**按空格**打一个标记，睁眼再按一下；空格只往日志里写一列，
不改变程序任何行为，它是判决用的 ground truth。

判决：`python tools\analyze_fuse_l4.py runs\session2.csv --png runs\fuse_l4.png`

**protocol 的三个约束都是量出来的，不是拍的**：

1. **闭眼 ≤ 5 秒、两次之间睁眼歇 ≥ 12 秒。** 由 8.2 的 c < 0.75 硬上限决定。
   （这里踩过一个坑：我一度把 protocol 改成"闭 12~15 秒"，理由是"PERCLOS 是
   17 秒平均、短闭眼会被稀释成噪声"。那个理由对 PERCLOS 成立，但**同一份数据
   上还有第二个更紧的约束**，两个约束方向相反。）
2. **全程盲测，不看屏幕。** 内置摄像头就在屏幕上，看输出这个动作本身会让头动、
   让闸门关闭、把 27 秒热清零。live 时只允许看两个颜色（标记是否变品红、闸门
   是否绿）。**这一条不是洁癖**：早先一版实验室数据里 90% 的闸门开启段都短于
   27 秒，那大半就是"看屏幕"造成的。
3. **闭眼时头不许动**（背靠椅子）。支路一正是靠头下垂判疲劳的——闭眼的同时
   让头沉下去，等于亲手把闸门关上。

### 8.7 结果

| | 第一场 | 第二场 |
|---|---|---|
| 会话时长 | 138.4 s | 153.6 s |
| 闸门开启占比 | — | **93.3%** |
| 闭眼段 | 2 段 18.2 s | 6 段 35.0 s |
| 可用标记拍 | 74 / 106 | **187 / 191** |
| EAR_norm 中位（闭眼 vs 睁眼） | 0.514 / 0.974 | 0.521 / 0.986 |
| 闭眼帧占比（闭眼 vs 睁眼） | 1.000 / 0.156 = **6.4×** | 0.995 / 0.130 = **7.7×** |
| **闭眼时的头动范围** | 3.3° | **1.4°** |

**结论：两场独立会话、共 8 次主动闭眼，EAR_norm 全部同向下降（−47%），
闭眼帧占比抬升 6~8 倍，而同期头部只动 1.4~3.3°（判据线 8°）。
支路二读的是眼睛，不是头姿——这一条现在有真人复现证据。**

**判决的护栏（口径必须随结论一起报）**：判决脚本先剔掉"基线已塌"的拍，
用两把独立的尺子——**标记尺**（尾窗 10 秒内标记占比 ≤ 0.70）和 **EAR 尺**
（原始 EAR 直接数闭眼占比 ≤ 0.70，不依赖用户按没按空格）。剔除量照实报
（第二场 4%，第一场 11%）。**"剔过之后成立"不等于"全程成立"。**

而真正要证的那件事是**可以直接量的**：`ear / EAR_norm` 就是当时那个 p75
基线。健康时它该落在睁眼区间——两场实测 0.371 / 0.376，对上全场睁眼参考
0.401 / 0.398。**不需要相信任何阈值。**

### 8.8 ⚠️ 支路二的局限（必须在报告中如实说明）

1. **冷启动 27 秒**：开场 27 秒内它一句话都说不了（实测首次出数 t = 30.3 s）。
   演示靠 protocol 的热身段绕过，但代价真实存在。
2. **真实驾驶场景下它比演示里脆弱得多**：演示场次（人坐着、不看屏幕）闸门开启
   93.3%、关闭事件只有 1 次、最长连续开启 133.5 s；但真实开车时扫后视镜、
   看侧窗是常态，闸门会频繁关闭，每关一次 27 秒热身清零——**那样它永远热不满**。
   **不能拿"演示里 93.3% 开着"去暗示实际路况也这样。**
   （缓解方向是把闸门关闭时的 `fb.clear()` 改成"冻结"，但要让 `full()` 的跨度
   判据和 `brate` 的分母一起改，见第 11 节。）
3. 判据线（头动 8°）和标定集都小，**这一路目前只适合"提示"，不适合"报警"**。
4. 真人验证同样是**单人**（见 7.4 第 3 条）。

## 9. 性能实测

测试环境：Intel Arc 核显 / 18 逻辑核 / **无独立 NVIDIA GPU**，全流程 CPU。

| 项目 | 实测 |
|---|---|
| MediaPipe `full` 纯推理（1280×720，画面中有人） | **16.6 ms/帧 = 60 FPS**（中位 16.4，最慢 18.4） |
| MediaPipe `lite` 纯推理（同上） | 15.3 ms/帧 = 66 FPS |
| 模型加载 | full 0.90 s / lite 0.09 s |
| **摄像头实际采集帧率** | **10 ~ 11 fps**（1280×720，室内灯光） |
| 单段 10 s 视频骨骼提取 | 2.4 s |
| 24 段全量提取（约 6.2 分钟素材） | 118.9 s |
| 训练（60 epoch，CPU） | 46.7 ~ 84.3 s |
| 24 段逐帧回放推理 | 约 12 s |

⚠️ 表里带"24 段"的两行是 24 段时代的。106 段时的训练实测：60 epoch 一个
epoch 约 3.3 s、总计 **200.5 s**（`runs/20260922_200934`）——已经翻倍，
但离"影响现场演示"还差得远。**这几行是工程账，不是性能指标。**

**结论：实时链路毫无压力。** 骨骼提取 60 FPS、Transformer 前向 < 5 ms，
而摄像头本身只有 10~11 fps——**瓶颈在摄像头，不在算法**。
这意味着后续若要提升帧率或分辨率，算力仍有充足余量。

**加入支路二之后的负载**：`src/fuse.py` 在同进程里多跑一个 FaceMesh 与一路
逻辑回归。性能自检（`runs/fuse_selftest.txt`，200 帧回放）：

| 环节 | 中位 | p95 |
|---|---|---|
| Pose | 18.9 ms | 37.8 ms |
| **FaceMesh** | **12.2 ms** | 18.6 ms |
| 支路一前向 | 2.2 ms | 2.9 ms |
| **合计** | **31.0 ms → 32.2 FPS** | |

**32 FPS 远高于摄像头本身的 10~11 fps，两路不是算力问题。**
真人会话里实测的决策频率是 5.4 Hz（`runs/session2.csv`，837 拍 / 153.6 s），
低于 `DECIDE_HZ = 10` 的名义值——**这一项的成因没有单独测过**：回放自检
证明两路合起来仍有余量，所以最可能是那场会话的**摄像头实际帧率偏低**
（暗光下自动曝光会把帧率拖下去，`live_fuse.bat` 里专门提示要盯 `cam x.x fps`，
低于 12 就该开台灯），而不是 FaceMesh 拖慢的。若现场 CPU 吃紧，
`--face-hz` 是给定的降载开关。

**闸门在回放数据上的行为**（`runs/fuse_replay_full.txt`，30 段）：`glance` /
`phone` / `fatigue` 三类共 15 段的闸门开启率**全是 0.0%**，而 `normal` /
`talking` / `yawn_open` 全是 100.0%——**闸门按设计工作**。哈欠规则在 5 段
`yawn_open` 上分别抬起 55/17/76/42/57 帧，在 3 段 `talking` 上**一帧都没抬**。

## 10. 工程实现要点

- **单进程单 extractor。** MediaPipe 1.0.1 的 Tasks 绑定析构固定耗时 42 秒，
  且每个实例都要付一次（真实检测只要 2.3 秒）。早期版本每个视频建一个 extractor，
  40 个片段光析构就白等 28 分钟，现象却表现为"模型推理慢"。
  现在的做法是全程复用一个，并在 `main()` 最后一行用 `os._exit(0)` 跳过析构。
- **推理主循环按媒体时间调度**，而不是墙上时钟：摄像头路径取真实流逝秒数，
  回放路径取 `frames / fps`。这样 `--fast` 快进回放才是"把整段视频快速过一遍
  完整链路"，结果与实速回放逐帧一致。
- **灯光输出统一入口。** `LightOutput.set_level()` 只在**级别变化时**被调用，
  屏幕模拟与串口（接 Arduino 灯带）走同一入口。接硬件时主循环一行都不用改，
  且不会变成每帧都发串口。
- **语音走后台线程 + 有界队列**（满则丢弃），绝不阻塞推理循环；
  用 Windows 内置 `System.Speech`，不依赖第三方库，现场不联网。

## 11. 后续工作

1. **补采数据**：数量已达标（每类 26~27 段），下一步要换的是**房间、光照、
   坐姿、距离和参与者**——这是当前最大的风险项（见 7.4）。
2. **补采后压窗口**：`normal` 类补足后可把窗口压到 30 帧，响应延迟再降约 0.6 s。
3. **硬件灯带**：Arduino 端固件与串口协议（PC 侧接口已就绪）。
4. **跨域测试**：在比赛场地用同一套设备实测，作为最终性能口径。
5. **闸门关闭时的处理**（支路二，见 8.8 第 2 条）：现在是 `fb.clear()`
   把 27 秒缓冲连**归一化基线**一起扔掉。基线是**个人生理特征**，扭头之前的
   值其实仍然有效，而且 `fb.push()` 本来就已经把污染帧挡在外面了（`clear()`
   是第二刀）。改成"冻结"能消掉每次扭头后的 27 秒冷启动。**但两处要一起改**：
   `full()` 判的 `span >= HIST_SEC` 会把中间的扭头空档也算进跨度（让"热满了"
   提前为真），`brate = 眨眼数/时长×60` 的分母也会被空洞撑大。
6. **材料口径**：8.7 的数字要连着护栏口径一起报（剔了多少拍），
   不能写成"全程成立"。
